# 写出便于人阅读的科研代码

以研究者能够看懂、检查和修改为目标。默认服务于自用科研 Python：让研究步骤和计算假设直接可见，不为未提出的公共接口、配置能力或未来扩展建设框架。其他语言借鉴同样的可读性原则，保留语言及框架确实需要的结构。

## 适用范围

将这些规则用于当前任务新增或修改的代码。不要顺便清理周围代码、重排整个文件，或扩大为全项目重构；用户明确要求整理的范围除外。维持既定计算方法、输入输出、副作用及必要的资源管理。遇到风格与项目现有格式检查冲突时，遵守项目约束，不擅自停用或重配格式化工具。

## 主流程与状态

- 按实际任务顺序组织代码，让读者容易辨认准备输入、处理、计算、输出等阶段。异步任务也应让启动、等待、重试和结束的关系清楚，不为表面线性改变执行语义。
- 将紧密相关的数据变化放在附近；缩短中间变量和状态标志的作用范围，减少跨几十行追踪初始化、重置和使用。状态确有必要时保留，用名称说明其含义和计数口径。
- 使用直白的条件和循环。简单 NumPy/pandas 运算、推导式和短方法链可以保留；多层条件表达式、嵌套推导式或长链增加理解负担时，展开为步骤和有意义的中间变量。
- 结束、继续和重试条件应容易定位。不要仅为缩短正文，将关键判断藏进回调、通用分发器或多级转发调用。

## 封装需要实际收益

先理顺必要逻辑，再决定是否提取函数。函数适合真实复用、有明确输入输出的独立计算、隔离复杂细节或明显缩小变量作用域。仅调用一次的函数也可能有价值；函数数量、调用次数和行数都不是机械判定标准。

仅转发参数、不增加含义的包装默认省去。不因假想复用引入 manager、factory、注册表、配置框架或通用流水线；也不要为避免函数复制多份相同计算。保留真实需要的类和框架结构，例如 PyTorch 模型。名称或简短说明应准确交代写文件、修改状态等重要副作用。

## 机制应与实际任务相称

实现功能前，先确认现有库、SDK 或框架已提供什么能力及保证，能直接满足任务时优先使用。新增机制须有实际任务或依赖契约依据，不把猜测的风险提升为额外需求，也不擅自扩大操作的前置条件。记录信息、检测变化和阻止执行各有不同用途，不自动将前两者升级为禁止继续。评估方案时同时考虑正常修改、继续实验和维护的成本；若常规工作必须绕过自建机制才能开展，应重新审视该机制。已有明确契约仍需保留，调整限于当前任务授权范围。

## 逻辑分段与视觉留白

将空行作为表达结构的一部分主动使用。同一个小目标内的语句紧密排列，切换到另一个逻辑步骤时通常空一行。较长、较密的代码块应检查能否分为有意义的小段，让读者不逐行细读也能辨认主要阶段。

不要按固定行数插空行，不要每条语句之间都空一行，也不要用连续多行空白代替结构整理。较大的阶段需要说明时，加一句简短的目的性注释；避免复述每一行代码。

简单调用、列选择、rename、merge 等操作在容易阅读时保持一行。多层逻辑应展开；多个彼此独立的配置项宜分行呈现。一个清楚的动作可以紧凑，多个独立决定不要挤在一起；不要用分号或密集表达式追求最少行数。

## 对防御措施做必要性判断

添加或保留 try/except、输入检查、备用路径、重试、hash 校验等措施前，在内部回答以下问题，不必向用户逐项汇报：

1. 它防的具体情况是什么？依据来自任务要求、真实输入、依赖契约、已有故障还是仅仅猜测？是否擅自扩大了任务要求？
2. 不做会怎样？原生错误已经足够清楚，还是会静默算错、丢失结果、重复提交任务或留下资源？
3. 做了有什么实际收益？是在恢复、释放资源、增加必要诊断信息、保护计算假设，还是仅仅包装错误或返回默认值？
4. 代价多大？它是否打断主流程、增加嵌套、分散状态，或给后续实验、正常修改和恢复操作增加门槛？
5. 能否更直接地实现相同目的？例如依赖已有保证，在合适入口检查一次，或保留原生异常传播。

根据实际收益及阅读、使用和维护代价选择最简单的充分措施。不要只因“更稳健”添加防护，也不要仅凭“像防御性代码”删除现有保证。Python 类型注解本身不证明运行时输入一定合法；测试通过也不单独证明现有检查多余。

### 异常与失败策略

新增科研脚本默认让未处理错误清楚地暴露。没有明确恢复策略、必要清理或额外诊断价值时，通常无需捕获后打印、包装或继续。不自行用空表、零值、备用文件、缺列补齐或跳过样本让失败看似成功；缺失值处理和允许部分成功须来自分析需求。

已有异常处理先查清用途。风格整理不擅自改变失败策略、取消语义、脱敏要求或资源释放保证。需要改变这些行为而任务意图不明确时，说明具体取舍并询问；普通风格判断自行完成。

必要的异常处理应有清楚的作用范围，避免整段主逻辑被多层恢复与清理机制淹没。只有核实生命周期和依赖能力后才替换清理结构；不要仅将复杂性藏进另一个函数。包装异常时评估原始类型、异常链和定位信息的价值，同时保留必要的敏感信息保护。

### Hash 校验

先说明校验需要确认什么，以及结果如何影响后续行为。下载完整性、内容寻址缓存或研究溯源可能确实需要 hash，应按具体要求保留。对刚生成的本地中间文件或每个处理阶段，不默认增加重复计算、重复比对或多套校验；只有实际契约或风险支持时才做。Hash 不自动证明来源可信，也不替代数据内容和科学假设检查。

## 完成前检查

只检查本次修改：主流程能否顺着读懂？是否依赖远处的隐含状态？是否有无收益的跳转、封装或防护？逻辑段之间是否有足够留白？是否为省行数增加了理解负担？正常修改后是否还能按既定契约继续工作？是否保持任务要求及必要的正确性保证？

按修改风险验证实际行为，尤其关注结果与失败路径；不要为风格规则建立函数数、空行数、行长配额或仅匹配文本的测试。交付时简短说明实质变化及必要的取舍，不输出整份自省清单。

需要校准 Python 的留白、表达式、封装或防御边界时，读取 [Python 正反例](references/python-examples.md)。这些例子用于理解判断方式，不要求将它们的结构套到所有任务。
